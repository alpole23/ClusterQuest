Cost of a Million Genomes

Two full pipeline runs — the Pantoea genus and the Erwiniaceae family that contains it — measured end to end, then extrapolated. Measured on a clean run from an empty results/. A million genomes costs about $1,140 internal / $1,515 external in compute — cheap enough that it is not the constraint. What stops you is memory: BiG-SCAPE needs ~1.9 TB of RAM to cluster that many BGCs in one pass.

Three scaling regimes

The two runs are far enough apart to separate the stages by how they respond to more genomes. This is the part that governs a million-genome plan — not the absolute numbers above.

The GTDB-Tk result is the useful surprise

Fitting the two points as fixed + per-genome gives 11.5 CPU-h per invocation plus 1.2 CPU-s per genome. The fixed term is 97% of a 2,758-genome run. That inverts the usual advice: for GTDB-Tk you want few, large batches, and batch size is worth more than any other tuning knob available.

antiSMASH scales with base pairs, not genomes measured

Per-genome cost fell from 98.0 to 80.4 CPU-seconds when the taxon widened. Nothing got faster — the genomes got smaller. Erwiniaceae includes 213 Buchnera endosymbionts with ~0.6 Mb genomes, and they pulled the mean down.

The 104 GB that was never there measured

Nextflow's trace reports peak_rss of 104 GB for GTDB-Tk. This machine has 56 GB of RAM. Both runs completed.

Three independent lines say the figure is an artefact. It did not move between runs — 104.3 GB on 1,736 genomes, 104.0 GB on 2,758 — which no real working set does under a 59% larger query load. It exceeds physical memory plus swap (88 GB), so it cannot be unique resident memory. And a 30-second sampler running alongside the Erwiniaceae job recorded what the kernel actually did:

Nextflow sums RSS across a process tree, and pplacer forks children that all map the same GTDB reference database — so every shared page is counted once per child. Even pplacer's own 47 GB is mostly file-backed mmap, which is why system memory in use never passed 19.2 GB at the same moment.

The SLURM allocation is a judgement call, not a measurement

process_high_memory requests 128 GB. Nothing measured needs it: file-backed pages are charged to a cgroup but stay reclaimable, so they should be evicted under pressure rather than trigger an OOM kill. The request stands because the failure modes are asymmetric — an OOM kill costs a 90-minute task and its queue slot, the over-request costs about $0.05.

It is not free of consequences. At 8 cores, 128 GB tips the billed dimension from cores ($9.52/day) to memory ($10.24/day). If GTDB-Tk is ever sharded across many concurrent jobs, that premium multiplies — re-measure with sacct -o MaxRSS, which reports per-step RSS rather than a summed figure, before paying it at scale.

Two changes did it. publish_mode = 'link' hard-links published output, so a file and its work/ counterpart share an inode — du across both now reports 71.2 GB where the apparent size is 118 GB. And NCBI_DATASETS_DOWNLOAD publishes only metadata, since RENAME_GENOMES republishes the genomes anyway: 24 GB became 10 MB.

It is not the 16 MB/genome an earlier draft projected. That assumed dropping the raw-download publish removed the data entirely; it only removed the second copy. work/ still holds 23.5 GB of raw download, because the task that fetched it has to keep its output.

GTDB-Tk transiently needs 94 GB of scratch

Nothing had measured this. While GTDBTK_CLASSIFY runs, its task directory holds 98 GB — 94 GB of it scratch_tmp — which is released on completion, leaving 2.7 GB of output. It is the peak-disk driver for the whole pipeline, and it is additional to the 140 GB reference database the config already warns about.

On a cluster where workDir sits on a quota'd scratch filesystem, that is an allocation requirement rather than a footnote. Measuring settled storage after a run, as every earlier figure here did, misses it entirely.

I/O did not improve and is the number to watch on a shared filesystem: 8,883 GB of reads and writes for 2,758 genomes, about 3.2 GB per genome, most of it small-file traffic that parallel filesystems handle worst.

44 days is a scheduler artefact, not a compute cost — batching antiSMASH cuts it to 11

Every genome is its own antiSMASH job today. At the cluster's submitRateLimit = '20/1min', submitting a million of them takes 833 hours before any queueing, against 55 hours of actual compute at queueSize = 200. The scheduler is the bottleneck by 15×.

The pipeline already batches its short per-genome steps for exactly this reason; antiSMASH was left unbatched because at 39 s per genome it did not look short. At a million genomes it is the single largest lever on wall clock, and it costs nothing in CPU-hours. After that the limits are BiG-SCAPE, which is one unsplittable job, and the serial NCBI download.

Memory is the wall, and it only appears above 4,000 BGCs

Peak RSS looks harmless across the first seven sizes — 1.62 to 3.40 GB — which is why an earlier draft of this page concluded memory was not a constraint. It was measured over a range where memory growth had not started. Extending to 10,000 BGCs shows the local exponent going 0.11 → 0.29 → 0.59 → 1.27 → 1.63 → 2.01. Above ~4,000 BGCs it is exactly quadratic.

Fitting GB = 1.14 + 1.29×10⁻⁷·n² gives ~1.9 TB of RAM at 121,000 BGCs, and 4.3 TB at Pantoea-level BGC yield. No single node runs that. The practical ceiling for one BiG-SCAPE job:

The database estimate held

Bytes per comparison converged to 101 (267 → 101 across the sweep), so 121,000 BGCs means 7.3 billion rows and ~0.74 TB in one SQLite file; 16.9 billion rows and 1.71 TB at the higher yield. Real, but a smaller problem than the RAM.

Compute for a million genomes lands near $1,140 internal and $1,515 external, which is small enough that it is not the constraint. Wall clock and scheduler behaviour are. At the campus limit of 20 submissions/minute, one job per genome is 833 hours of pure submission — which is why the short per-genome steps are already batched and antiSMASH is capped at 2 CPUs.

What to change before scaling

Ordered by how much they matter for a run 360× larger than the one measured.

  1. done
    BiG-SCAPE scaling, measured 29 Aug

    Ten-point sweep, 333 → 10,000 BGCs, via scripts/bench_bigscape_scaling.py. Cut the compute projection from 21,000 to ~1,090 CPU-h, and found the real limit: peak RSS turns quadratic above 4,000 BGCs, reaching ~1.9 TB at 121,000.

  2. build
    Shard GTDB-Tk into large batches

    Currently one invocation per run. At 50,000 genomes per batch the stage costs $30 instead of $240, purely from amortising the reference-tree load.

  3. verify
    Confirm GTDB-Tk memory with sacct -o MaxRSS

    The 128 GB request is insurance against a number we have good reason to believe is wrong by 2×. One cluster run settles it, and 64 GB would keep cores as the billed dimension.

  4. plan
    Partition BiG-SCAPE — it cannot run in one pass

    A single job caps at ~31,000 BGCs on a 128 GB node and ~22,000 on the 64 GB the SLURM profile allocates. A million genomes needs the comparison partitioned — by BGC class, or by a pre-clustering pass — since one all-pairs run over 121,000 BGCs needs ~1.9 TB of RAM and a 0.74 TB database.

  5. watch
    Small-file I/O, not capacity

    3.2 GB per genome of read+write, spread across thousands of tiny files per directory. Capacity at 8.15 TB is trivial; metadata operations on a parallel filesystem are not.

  6. note
    GCF numbers are per-run identifiers

    BiG-SCAPE's family.id follows file discovery order. Comparing the two Pantoea runs, all 13 families had identical membership and 9 came back with a different number. Cite GCF numbers against a specific run, never across runs.

Method. Both runs on one machine, local executor, 56 GB RAM + 32 GB swap, conda environments. CPU-hours are realtime × cpus summed from pipeline_trace.tsv. Costs apply the configured SLURM allocations to the measured durations; no run was executed on SLURM. Memory sampled every 30 s from /proc via free and ps.

Reference data. GTDB r226 (what gtdbtk 2.6.1 declares as its minimum), Pfam 38.2, NCBI taxdump 2026-08-01 — pinned in nextflow.config and recorded in software_versions.json as db_gtdb_release, db_pfam_release and db_taxdump_date. Every figure on this page comes from a run that states what produced it.

Genome counts use the pipeline's own NCBI query — --assembly-source GenBank --exclude-atypical. Detection is phosphonate-only (--hmmdetection-limit-to-rule-names phosphonate); a general antiSMASH run would cost substantially more.
